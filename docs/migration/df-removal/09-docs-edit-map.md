# 09 — Docs edit map for the DataFusion removal

This wave produces **the map only**. Nothing here has been applied. No existing
file was modified in producing it.

Scope: the 38 files returned by

```sh
grep -rl -i datafusion docs site README.md ROADMAP.md CAPABILITIES.md WEDGE.md CHANGELOG.md benchmark
```

plus the root `Cargo.toml`, which is out of that glob but carries the
version-pinning discussion the brief asks about. **212 mentions total** (209 in
the 38 files, 3 in `Cargo.toml`).

`docs/decisions/0030-own-query-engine-remove-datafusion.md` landed while this
map was being written and is the superseding vehicle; it is excluded from the
edit map because it is the successor document, not a target of the sweep.

## Classification key

| Tag | Meaning | Action |
|---|---|---|
| **HISTORICAL** | Records a past decision or a benchmark run that happened | **Preserve verbatim.** Do not rewrite history to match the present. |
| **CURRENT-ARCH** | Describes how Basin works today | **Rewrite** when the engine lands |
| **MARKETING** | `site/*`, README headline claims — user-visible | **Rewrite**, highest care |
| **INCIDENTAL** | Passing reference, low effort | Rewrite or drop, no judgement needed |

`Blocking?` means: **can the docs sweep apply this edit mechanically?**
`no` = a text edit. `YES` = blocked on a code change, a generator, or an
engineering answer that does not exist yet.

## Part 1 — The at-risk claims (read this before editing anything)

Six things become false or unverifiable the moment `datafusion = "53"` leaves
`Cargo.toml`. They are ordered by public exposure.

### R1 — The published win table is attributed to DataFusion's optimizer. BLOCKING.

`README.md:88-101` publishes LATERAL JOIN **462×**, star join **261×**,
correlated subquery **113×**, range scan **81×**, `PERCENTILE_CONT` **19×**, and
~20 more analytical shapes. ADR 0030's own Context paragraph states these "are
produced by DataFusion's logical optimizer and vectorised executor, not by
anything Basin wrote."

The numbers do not become *false* — they were measured — but they stop
describing the shipping engine. The same is true of the two README badges
sourced from analytical cards and of every `RESULTS_*.md` analytical row.

**These must be re-measured on the owned engine before the removal commit is
public, not re-attributed.** ADR 0030 already names the kill criterion (2×
regression on any headline shape). The docs sweep must not touch these rows; a
separate wave regenerates them from the integration tests. If any headline
number regresses, the honest move — and the one consistent with the badge that
says `benchmarks-honest_wins_and_losses` — is to publish the regression on the
same card, not to quietly drop the row.

### R2 — The version lockstep loses a leg, and ADR 0015 is immutable.

`Cargo.toml:128` (`datafusion = "53"`), ADR 0015 lines 111, 120, 251, and 279
all encode the **arrow 58 / DataFusion 53 / vortex 0.71** three-way pin. After
removal it is a two-way pin: arrow 58 / vortex 0.71.

Per `docs/decisions/README.md` rule 1, **ADR 0015's body must not be edited.**
The lockstep sentences stay exactly as written; ADR 0030 already records the
change (line 137: "loses one of its three legs"). ADR 0015 gets a status line
and nothing else. `Cargo.toml` is a live file and is edited normally.

### R3 — Vortex is read *through* `vortex-datafusion`. BLOCKING.

`CAPABILITIES.md:172`, ADR 0015:119-120, ADR 0015:279 all state the read path is
`vortex-datafusion` 0.70's `VortexFormat` implementing the DataFusion 53
`FileFormat` trait. ADR 0030:159-161 lists this as **"being assessed as a
potential blocker"** and ADR 0030:192 makes it a kill criterion.

**No replacement text can be drafted for `CAPABILITIES.md:172` until that
assessment concludes.** Whatever replaces it is a factual description of a read
path that does not yet exist. Leave the row untouched and revisit.

### R4 — The generated benchmark cards say "DuckDB beats DataFusion". BLOCKING.

The `viability_analytical` claim string —

> "On a 1M-row aggregate (count + avg + sum-of-lengths) with GROUP BY across 10
> Parquet files, the DuckDB-backed analytical engine beats the
> DataFusion-on-listing-table OLTP engine by at least 1.5x on the same dataset."

— appears in **8 generated artifacts** (`benchmark/data*/results.js`,
`benchmark/data*/viability_analytical.json`, and the three `RESULTS_*.md`
cards). These are regenerated by `benchmark/run/run_all.sh` +
`benchmark/bundle.py` from an integration test. **Editing the artifacts is
pointless — they regenerate.** The claim string lives in the test source under
`tests/integration/`, outside this sweep's scope.

Compounding: the card compares against DuckDB, which `CAPABILITIES.md:170`
records as already removed. The card is describing a two-engine architecture
that no longer exists. This card should probably be **retired**, not reworded —
flag for the benchmark wave.

Also generated: `benchmark/data/results.js:5525` and `:5605` contain captured
error strings (`table 'datafusion.public.__diesel_schema_migrations' not
found`). Those are **recorded ORM-suite output from a run that happened** —
HISTORICAL, and they will change on their own when the engine's error text
changes. Do not hand-edit.

### R5 — "Basin does not fork DataFusion" and the Apache attribution.

`README.md:330` currently promises "every query plan runs through upstream
operators." Fully false post-removal.

Note the provenance: `CHANGELOG.md:4579` and `:4702` record that the Apache
DataFusion attribution was **deliberately added** (commit `4e1f87c`). Removing
an attribution is correct once the dependency is gone, but ADR 0030 goes out of
its way to call the debt "real … owed to a good library." **The replacement
text below keeps that acknowledgment rather than erasing it.** Silently
deleting the credit would be the one edit in this sweep that reads as dishonest.

### R6 — "inherits DataFusion's upstream limits". VERIFY.

`README.md:159` and `README.md:396` both say Basin "inherits DataFusion's
upstream limits on a handful of shapes (recursive CTE, exact
COUNT(DISTINCT))." Post-removal there is no upstream to inherit from.

Whether the *limits* persist is an open question for the engine wave. Do not
assume they vanish, and do not assume they remain. Draft text below marks it
`VERIFY` — the sweep must confirm against the owned engine before publishing
either version. Same for `CAPABILITIES.md:467` (`WINDOW … EXCLUDE`), where the
stated trigger — "will close when sqlparser ships `WindowFrameExclusion`" —
becomes meaningless because libpg_query already parses the clause.

## Part 2 — ADRs needing a status line

`docs/decisions/README.md` rules, verbatim: *"Don't edit accepted ADRs. To
change direction, write a new ADR that supersedes it. The old one stays as
historical record."* The `Format` block permits
`Status: Accepted | Superseded by NNNN | Withdrawn`.

The successor exists: **ADR 0030, Accepted 2026-08-12**. So the permitted work
is a one-line status change per ADR, plus the index table. **Do not touch any
Context / Decision / Consequences prose in these files.**

The repo has no precedent for "Amended by" as a literal status value; ADR 0015
sets the house precedent for a partial revision — it keeps `Status: Accepted`
and appends a dated update line. Recommendation: use
`**Amended by [ADR 0030](./0030-own-query-engine-remove-datafusion.md)
(2026-08-12)**` appended to the existing Status line, since none of these
decisions is *reversed* — each has its mechanism replaced. Confirm with the
maintainer before applying; this is a convention call, not a mechanical one.
