## Methodology

### Workload

The same three files are applied identically to all three endpoints:

| File | Purpose |
|---|---|
| `three_way_schema.sql` | Creates `bench_three_way.events` (BIGINT id, UUID project_id, TEXT action, TIMESTAMPTZ created_at, TEXT payload) |
| `three_way_queries.sql` | Documents Q1–Q4 verbatim |
| `run_three_way.sh` | Drives schema creation, bulk insert, timed query battery, teardown, and JSON emission |

**Data volume:** {{ROW_COUNT}} rows (default 100,000 — matches the Basin real-S3
compare_postgres benchmark so results are cross-comparable).

**Query battery (identical SQL, all three endpoints):**

| Query | SQL shape | What it measures |
|---|---|---|
| Q1 — Point query | `WHERE id = N/2+7` | Selective single-row lookup; no index on any endpoint — pure substrate predicate evaluation |
| Q2 — Range scan | `WHERE id BETWEEN N/4 AND N/4+10000` | ~10,000-row sequential window; tests columnar/heap scan efficiency |
| Q3 — Aggregate | `SELECT id/1000, COUNT(*), SUM(id) GROUP BY bucket` | Full-table aggregate; tests engine throughput |
| Q4 — Disk size | `pg_total_relation_size('bench_three_way.events')` | Storage cost in bytes; null if function unavailable on platform |

**No indexes** are created on any endpoint.  This is an intentional substrate
comparison: we are measuring how each platform stores and scans data, not how
well it uses B-tree indexes.  A Postgres endpoint with an index on `id` would
be faster for Q1 and Q2 — that is not the scenario being measured.

### Fairness notes

- **Same region, same test client.** All three endpoints are in Frankfurt
  (`fra`).  The benchmark client is also run in Frankfurt or as close as
  possible.  The operator is responsible for confirming region co-location;
  the harness stamps the `REGION_LABEL` env var into the JSON but cannot
  verify routing independently.
- **Connection setup excluded from query timing, included in insert timing.**
  Each query iteration is timed individually starting from the `psql` dispatch
  call.  Connection establishment to the persistent psql session is _not_
  included in per-query latency.  The bulk insert timing (wall-clock) does
  include the connection setup for the session that executes INSERTs.
- **Cold vs warm.** Queries are issued sequentially within a single session
  without an explicit cache-flush between iterations.  The first iteration may
  be colder than subsequent ones; p50/p95 across {{ITERATIONS}} iterations
  captures both the warm and any warm-up variance.  There is no explicit cold
  measurement in this harness (unlike the OSS `compare_postgres.rs` cold-start
  test).  Operators who want a cold p50 should restart the test with
  `ITERATIONS=1` and issue it from a freshly connected session.
- **Iteration count.** Default is {{ITERATIONS}} iterations per query per
  endpoint.  p50 = median; p95 = 95th percentile across those iterations.
- **Synthetic data.** Rows are generated by a deterministic formula
  (`payload-<zero-padded-id>`).  Real-world data distributions (cardinality,
  skew, compression ratio) will differ.
- **No platform tuning.** All endpoints are used with default settings — no
  `shared_buffers`, `work_mem`, connection pool overrides, or custom indexes.
  A tuned endpoint would close or widen some gaps.
- **pg_total_relation_size.** This function reflects Postgres heap storage and
  is accurate for Neon and Supabase (both are vanilla Postgres-based).  Basin
  Cloud stores data in Vortex/Parquet on object storage; if
  `pg_total_relation_size` is unavailable or returns a synthetic value, the
  metric is recorded as `null` with a note.  This is an honest null, not a
  fabricated number.

## Caveats

- **Basin Cloud is not vanilla Postgres.** Basin speaks the Postgres wire
  protocol but its execution engine is DataFusion over Vortex/Parquet on
  object storage.  On analytical workloads (Q3) Basin may be faster or slower
  than Neon/Supabase depending on data volume and whether pre-aggregation is
  active.  On OLTP row lookups (Q1) Neon/Supabase (heap + btree indexes) are
  the expected leaders for large datasets.
- **Neon and Supabase use Postgres heap storage.** `pg_total_relation_size`
  reflects heap + TOAST + indexes.  For a fair storage comparison with Basin
  (which uses columnar Vortex), note that Postgres heap has significant per-row
  overhead (tuple headers, alignment, MVCC visibility bits).
- **Free-tier / serverless cold starts.** Neon and Supabase have serverless
  tiers that auto-suspend.  If either endpoint is on a serverless plan, the
  first connection may pay a cold-start penalty not reflected in query p50/p95.
  Run on always-on instances (Neon Pro, Supabase Pro) for a fair comparison.
- **These numbers were produced by the 3-way harness, not the Basin OSS test
  suite.** The OSS `compare_postgres.rs` test runs inside the Basin process;
  this harness measures only what crosses the network wire from a psql client.

./benchmark/three_way/run_three_way.sh
