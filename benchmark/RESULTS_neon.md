## Scaling

## Postgres head-to-head

### Analytical scans, 1M rows, COLD first-touch (Basin v57 vs Neon free)

_The same scans on a COLD first touch — Basin reads from object storage (Tigris) before its cache is warm. The big aggregations still win cold; top_k does NOT (the first-touch object-storage reads dominate). Published honestly. p50 ms, lower is better._

| Metric | Basin | Postgres | Winner | Ratio |
|---|---|---|---|---|
| sum(amount), numeric_only — SELECT sum(amount) FROM t | `46.98 ms` | `111.57 ms` | **Basin** | `neon / basin = 2.37x cold (WIN)` |
| count(DISTINCT tenant_id), wide_pk — SELECT count(DISTINCT tenant_id) FROM t | `85.85 ms` | `177.98 ms` | **Basin** | `neon / basin = 2.07x cold (WIN)` |
| group_by top20, wide_pk — SELECT tenant_id,count(*),sum(amount) FROM t GROUP BY tenant_id ORDER BY 2 DESC LIMIT 20 | `95.58 ms` | `122.08 ms` | **Basin** | `neon / basin = 1.28x cold (WIN)` |
| top_k, wide_pk — SELECT id,amount FROM t ORDER BY amount DESC LIMIT 50 | `811.00 ms` | `116.00 ms` | **Postgres** | `neon wins 7.0x cold (LOSS)` |

> Cold = first-touch p50 (caches empty, Basin pays the object-storage read). The disaggregated-storage tradeoff: Basin's cache helps repeat reads, not the first miss. top_k loses cold (811ms vs 116ms) even though it wins 3.64x warm — we publish the loss.

_DIFFERENT KIND OF WIN, labeled honestly: a bare count(*) with no predicate is served O(1) from Basin's maintained row-count metadata — Basin does not scan the table at all. Neon counts by scanning. We separate this from the scan wins on purpose. A maintained-count bug (DELETE of an absent PK reported 'DELETE 1' and corrupted count(*)) was found and fixed this cycle with an adversarial oracle test, so this metadata path is now correctness-gated.

### Where a row store still wins (Basin v57 vs Neon free)

_Honest losses, published. A row store (Neon) wins tiny warm point reads, and Basin loses cold first-touch reads across the board. We show these next to the wins. p50 ms, lower is better._

| Metric | Basin | Postgres | Winner | Ratio |
|---|---|---|---|---|
| 10k warm point op — SELECT ... WHERE id = $1 (single-row read) | `2.60 ms` | `0.90 ms` | **Postgres** | `neon wins ~2.9x warm (small-scale point read)` |

> At 10k rows, Neon's warm point read (~0.9ms) beats Basin's (~2.6ms). But Basin's per-query ENGINE compute for that read is only ~255us — the gap is connection-pool + network round-trip, NOT the query path. A row store wins tiny warm point reads; Basin's architecture targets analytical scans and elastic per-project storage. Cold first-touch reads also lose: Basin reads object storage (Tigris) ~25-50ms/file on the first miss vs Neon's local SSD. Also honest: PK bulk-COPY slows super-linearly with table size (practical ceiling ~100M today); no-PK ingest stays flat. Per-size warm verdict: 10k 11/21/2 loss, 100k 17/15/4, 1M 12/11/1.
